# Prompt 06 — C4 Architecture

Show the structure that realises the domain model and hosts the feature set — C4 answers **what**
the system looks like. The **why** behind each material choice belongs to the decision-record
stage that follows this one; do not argue trade-offs at length here, point to them as decision
candidates instead. C4 is the map; the decision record is the memory behind the map.

The risk-classification stage's tier-consequences table constrains this map directly: maximum
permitted autonomy, the human-oversight requirement, the logging floor, and any data-residency
limit all shape what containers and components may do — treat that table as binding, not
advisory.

## Artifact Status

State `stable` | `provisional`, inherited from the domain model's status unless new evidence
justifies an upgrade — if it changed, say why. If `provisional`, keep the map to the minimum
governed workflow and avoid an elaborate multi-agent topology until the evidence improves.

## System Context

Level 1: the people and roles, and the external systems, that interact with this solution. As a
mermaid `C4Context` diagram per house style, with a short narrative.

## Containers

Level 2: the independently deployable or runnable units — applications, data stores, brokers,
service and agent runtimes, and so on. As a mermaid `C4Container` diagram per house style, with a
short narrative.

## Components and Code

Level 3: the critical decision-workflow modules inside each container — rule engines, retrieval,
agents, and HITL interfaces where relevant — as a mermaid `C4Component` diagram. Go to Level 4
(key classes, interfaces, or modules) only where a path carries real risk; most components do not
need it, and ornamental detail is worse than no detail.

## Cross-Cutting Views

**Mapping** — each major architecture element to the bounded context it realises, and which
features (`FR-IDs`) land in which container or component. **Boundaries** — data, trust, privacy,
authority, and connectivity, across every level. **Degraded and offline mode** — behaviour when a
dependency or connection fails. **Prohibited operational write paths** — what this system must
never write back or mutate, consistent with the domain model's rules-vs-AI boundary. **Gen AI
runtime sketch** — where retrieval, model calls, tools, and human review sit in the container and
component view; structure only, the justification for each choice belongs in a decision record.

## Decision Candidates

List the architecture choices visible on this map that need a decision record — options visible,
decision not finalised here unless the evidence already constrains it to one option.

## Lean / DMAIC Lens

This stage's focus is **Improve** by architecture — removing integration, transport, and waiting
waste through the shape of the map itself, without introducing new waste. Record: whether the map
reduces transportation or integration waste (fewer hops, a clear system of record); where a
container could create waiting (a synchronous chain, a human-review bottleneck); the risk of
observability waste (logs or metrics with no owner) or context waste (state reconstructed
everywhere); and whether any container looks like overproduction against the minimum governed
workflow.

Do not invent domain language that contradicts the domain model — raise a domain issue instead of
silently changing it. Do not write full API schemas here; that is the technical-design stage. Do
not present a `provisional` map as production architecture.

Use exactly these `##` section headings, in this order: Artifact Status, System Context,
Containers, Components and Code, Cross-Cutting Views, Decision Candidates, Lean / DMAIC Lens.
